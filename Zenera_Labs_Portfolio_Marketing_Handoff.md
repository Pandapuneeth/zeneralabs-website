# **3\. Required Asset Package for Every Project**

**A. Working application —** Stable MVP that can be shown live or through a recorded demo.

**B. Demo video —** 5–10 minute recording showing the core workflow and at least one edge/failure case where the brief requires it.

**C. Screenshots —** 6–10 clean screenshots: landing/input screen, main workflow, core result, important settings, error/edge case, and final output.

**D. Architecture diagram —** Simple visual: frontend/input → backend/orchestrator → AI/ML components → storage/tools → output.

**E. README —** Problem, approach, architecture, stack, setup, example usage, validation, limitations and future improvements.

**F. Technical summary —** 1–2 page business-friendly summary for the website/capability deck. Do not expose secrets or sensitive internal data.

**G. GitHub link —** Clean public or approved repository with sensible structure and no credentials.

**H. CTA —** A final website section: “Need something similar? Talk to Zenera Labs.”

# **4\. Website Case Study Template**

**1\. Hero —** Project name \+ one-line value proposition \+ primary demo/screenshot \+ CTA.

**2\. The Problem —** 2–4 short paragraphs explaining the business problem, not the code.

**3\. The Zenera Solution —** What we built and how it changes the workflow.

**4\. Key Capabilities —** 5–8 concise feature cards with screenshots where helpful.

**5\. How It Works —** Simple workflow diagram with 4–8 steps.

**6\. Technology —** Frameworks, AI/LLM approach, database, APIs and deployment approach.

**7\. Validation —** Test scenarios, reliability checks, edge cases, and measurable observations where available.

**8\. Demo —** Embedded video or strong thumbnail linking to the demo.

**9\. Repository —** GitHub link, only if the repository is approved for public sharing.

**10\. Future Extensions —** 2–5 realistic improvements or integrations.

**11\. CTA —** “Have a similar workflow? Zenera Labs can build a custom version for your business.”

# **5\. Marketing Repurposing System**

1. Website: publish one polished case study per finished project.  
2. LinkedIn: create 3–5 posts per project — problem/insight, architecture, demo clip, technical lesson, and business use case.  
3. Instagram: create a 6–8 slide carousel and a 30–60 second demo reel.  
4. Sales deck: one slide per project with screenshot, capabilities, industries, and “Request Similar Solution” CTA.  
5. Proposals: reference only the 1–3 portfolio pieces closest to the prospect’s requirement.  
6. Direct outreach: use a relevant project as proof instead of sending a generic “we build AI” pitch.  
7. Channel partners: give the partner a capability deck they can forward to prospects without needing Zenera to explain everything from scratch.

# **6\. Content Rules**

* Never say “client” when the project was internally developed.  
* Use language such as “Zenera Labs Engineering Portfolio”, “Internally developed”, “Prototype”, “Reference implementation”, or “Selected AI Solution”.  
* Never expose API keys, credentials, private datasets, confidential client information or internal infrastructure details.  
* Do not overclaim accuracy or production readiness. State limitations where relevant.  
* Every public case study should have a clear business problem, solution, workflow and evidence of the working system.  
* Prefer real screenshots and real demo footage over stock graphics or generic AI imagery.

# **7\. Definition of Done for Each Portfolio Project**

* Working MVP is stable enough for a live demo.  
* GitHub repository is cleaned and approved for public/internal sharing.  
* README is complete.  
* Architecture diagram is prepared.  
* Demo video is recorded.  
* Screenshots are captured and named clearly.  
* One business-friendly case-study summary is written.  
* Technology stack and key capabilities are documented.  
* Validation/test evidence is included.  
* Portfolio webpage draft is ready.  
* LinkedIn/Instagram assets can be created from the package.  
* Final CTA and Zenera branding are applied.
